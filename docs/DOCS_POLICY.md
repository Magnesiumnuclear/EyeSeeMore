# DOCS_POLICY.md — 文件重整規則草案與撰寫公約

> 本文件定義 EyeSeeMore 文件系統的整理原則、分類規則與撰寫公約。
> 目標不是讓 docs 變多，而是讓每一份文件只承擔一種核心責任，降低重複、膨脹與失真。

---

## 1. 文件系統的核心原則

### 黃金法則

1. 一份文件只回答一種核心問題。
2. 優先新增職責單一的 `.md`，不要先增加資料夾層級。
3. 結構文件講邊界，功能文件講流程，模組文件講責任，流程文件講做法。
4. 不在多份文件重複維護同一段規則；若必須提及，只放摘要並連回唯一真理源。
5. README 只做導航與治理入口，不承載大量細節。

### 文件治理目標

1. 讓新加入的人可以在 5 分鐘內知道先讀哪些文件。
2. 讓接到任務的人可以在 10 分鐘內定位要修改的層、流程與模組。
3. 讓人類與 AI 在新增文件時遵守相同規則，避免 docs 再次失控。

---

## 2. 文件分類規則

未來 docs 採三層邏輯，但不急著做深資料夾：

1. 結構文件
回答「這個系統如何被組起來」。
適合內容：架構分層、依賴邊界、生命週期、資料流、訊號流。

2. 功能文件
回答「這個能力如何運作」。
適合內容：索引、搜尋、OCR、收藏、設定、匯入匯出等完整流程。

3. 模組文件
回答「這個模組或檔案做什麼」。
適合內容：責任、依賴、公開方法、常見修改點、風險點。

4. 流程與治理文件
回答「應該怎麼開發、修改、驗證、發版」。
適合內容：開發流程、公約、提交流程、文件撰寫規則。

### 採用順序

1. 先判斷內容是否屬於結構。
2. 若不是，再判斷是否屬於功能流程。
3. 若還不是，再考慮是否需要模組級說明。
4. 若內容是在規範行為，放到治理文件，不塞進架構文或功能文。

## 3. 重整後的建議角色分工

### 保留為骨架文件

- `README.md`：文件入口、閱讀順序、黃金法則、文件地圖
- `ARCHITECTURE.md`：系統架構、主要子系統、生命週期總覽
- `LAYERS.md`：分層規則、依賴邊界、放置新代碼的判斷規則
- `DESIGN_PATTERNS.md`：跨模組通用模式與反模式

### 保留為功能文件

- `INDEXER.md`：索引流程與相關設計
- `DATABASE_SCHEMA.md`：資料模型、表關係、資料一致性與 schema 策略

### 降級為索引或總覽文件

- `MODULES_CORE.md`：應改成 core 模組總覽，不再承載所有細節
- `MODULES_UI.md`：應改成 ui 模組總覽，不再承載所有細節

### 收斂為治理文件

- `CONTRIBUTION.md`：開發流程、修改流程、UI/i18n/QSS 規範
- `DOCS_POLICY.md`：文件規劃與撰寫公約

### 收斂為時間軸文件

- `ROADMAP.md`：未完成規劃、優先級、已知風險、預計方向

### 從大型文件拆出的候選新文件

以下不是現在必須一次建立完，而是未來拆分優先順序：

1. `SEARCH_FLOW.md`
說明搜尋查詢從輸入到結果顯示的完整流程。

2. `OCR_FLOW.md`
說明 OCR 推論、資料存取、UI 顯示與編輯鏈路。

3. `MODEL_LOADING.md`
說明模型加載、共享、延遲初始化與非阻塞策略。

4. `WINDOW_INTEGRATION.md`
說明 Win32、工作列、原生事件與視窗狀態整合。

5. `CORE_MODULE_INDEX.md`
只保留 core 模組索引與跳轉，不再容納過多細節。

6. `UI_MODULE_INDEX.md`
只保留 ui 模組索引與跳轉，不再容納過多細節。

7. `PERFORMANCE_NOTES.md`
集中維護已完成的效能優化、量測數據與設計取捨。

8. `MIGRATION_NOTES.md`
集中維護 schema、設定、檔案結構演進的遷移規則。

## 4. 何時新增新文件，何時修改舊文件

### 應新增新文件的情況

1. 新內容回答的核心問題，和現有文件主題不同。
2. 單一章節超過原文件責任邊界，繼續加入會造成主題混雜。
3. 新功能涉及完整流程，且跨越多個模組或多層。
4. 同一文件連續出現大量交叉連結，顯示內容已經耦合過高。

### 應修改既有文件的情況

1. 只是補充現有主題中的缺口。
2. 只是更新 API、欄位、行為差異。
3. 只是修正文內已存在的錯誤、過時資訊或例子。

### 不應做的事

1. 因為找不到地方放，就把內容塞進 `README.md`。
2. 因為不想新增文件，就把不同主題硬塞到同一份文件。
3. 在多份文件複製同一段規則，只改其中一份。

---

## 5. 何時增加資料夾，而不是增加 `.md`

現階段 docs 仍適合維持平面結構。只有在以下條件同時成立時，才考慮新增一層子資料夾：

1. 同類文件至少累積 3 份以上。
2. 單靠檔名已經不易掃描與定位。
3. 該分類在未來還會持續擴張。

### 可接受的未來資料夾

1. `docs/flows/`
放搜尋、OCR、索引、模型加載等流程文。

2. `docs/modules/`
放 core/ui 模組索引與模組專文。

3. `docs/governance/`
放 contribution、docs policy、release 流程等治理文。

### 暫時不建議

1. 按程式碼資料夾一比一鏡像整個 repo。
2. 建太深的層級，例如 `docs/core/services/search/`。
3. 先建資料夾，再把原本混亂內容原封不動搬進去。

## 6. 文件撰寫公約

### 6.1 每份文件必須先定義自己的責任

文件開頭應明確寫出：

1. 這份文件回答什麼問題。
2. 這份文件不回答什麼問題。
3. 需要時應轉去看哪一份文件。

建議格式：

```md
# 文件名稱

> 這份文件說明……
> 不涵蓋……；若要看……，請改讀……
```

### 6.2 標題結構規範

1. H1 只用一次。
2. H2 代表文件的主要章節。
3. H3 只用於章節內局部細分，不要把文件切成過深層級。
4. 若 H3 以下還需要大量展開，通常代表應該拆新文件。

### 6.3 內容密度規範

1. README 以索引為主，應短。
2. 結構文件應中等篇幅，重點在穩定原則與圖景。
3. 功能文件可以較長，但只能聚焦單一能力鏈。
4. 模組索引文件應輕量，避免寫成百科全書。
5. roadmap 應偏短到中等，不應承載大段已完成技術設計。

### 6.4 唯一真理源規則

同一類規則只能有一個主文件：

1. 分層規則以 `LAYERS.md` 為準。
2. 跨模組設計模式以 `DESIGN_PATTERNS.md` 為準。
3. 開發流程與 UI 規範以 `CONTRIBUTION.md` 為準。
4. 文件治理與撰寫公約以 `DOCS_POLICY.md` 為準。
5. 其他文件若需提及，僅寫摘要並加連結，不重寫完整規則。

### 6.5 範例與程式碼片段規則

1. 只保留有辨識價值的範例。
2. 同一概念不要重複貼多段近似程式碼。
3. 範例重點是解釋邊界、風險、時序與依賴，不是把實作再複製一次。

### 6.6 AI 與人類共同遵守的更新規則

1. 新增內容前，先判斷它屬於哪一類文件。
2. 若同時影響多份文件，先更新唯一真理源，再更新索引與摘要。
3. 若不確定該放哪裡，先新增短小專文，不要把內容塞進大總表。
4. 若一份文件開始同時回答兩個以上核心問題，應提出拆分。

## 7. 未來文件撰寫流程

### 新增文件時

1. 先寫一句這份文件的責任。
2. 檢查是否與現有文件重疊。
3. 在 `README.md` 新增入口。
4. 若該文件屬於某主題群，再由索引文加連結。

### 修改文件時

1. 先判斷是更新事實，還是改變規則。
2. 規則變更時，優先更新唯一真理源。
3. 事實變更時，同步檢查是否影響索引、流程文、roadmap。

### 刪除或合併文件時

1. 確認內容是否已被其他文件完整吸收。
2. 清掉 README 與其他文件中的舊連結。
3. 避免只刪入口、不處理引用。

---

## 8. 對專案當前狀態的具體規劃

### 第一階段

1. 在 `README.md` 最上方加入黃金法則與本文件入口。
2. 將 `DOCS_POLICY.md` 作為文件治理唯一真理源。
3. 保持 docs 平面結構，不先拆資料夾。

### 第二階段

1. 瘦身 `CONTRIBUTION.md`，只保留流程與規範。
2. 瘦身 `ROADMAP.md`，只保留規劃、風險、待辦與簡短歷史摘要。
3. 將 `MODULES_CORE.md` 與 `MODULES_UI.md` 逐步降級成索引文。

### 第三階段

1. 依需求拆出流程文件，例如搜尋、OCR、模型加載、效能筆記。
2. 當同類文件累積夠多，再考慮 `flows/` 或 `modules/` 一層資料夾。

---

## 9. 最終判準

若未來對文件放置位置有爭議，依下列順序判斷：

1. 這段內容回答的核心問題是什麼。
2. 是否已有文件專門回答這個問題。
3. 若沒有，新增新文件是否比擴充舊文件更清楚。
4. 若只是為了收納而收納，先不要增加資料夾。

只要記住一句話：

> 先讓每份文件單純，再讓整個 docs 有結構。
